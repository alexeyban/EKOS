1 · Source databases and what EKOS compiled from them

Each database is its own EKOS project, built by ekos eval bench prepare. The pipeline reads the database’s catalogue and its dictionary (database_description/*.csv): one generated schema.sql per project, holding CREATE TABLE statements plus one COMMENT ON COLUMN per dictionary row. That file goes through the normal pipeline (build → recover → resolve → compile → commit). Question files and gold SQL never leave the archive. After the build, every ledger is scanned for the text of all 500 questions, gold statements and evidence hints; the scan was clean (1,349 texts, no hit).

8 · How it works, and what it costs to run

Pipeline

  1. Prepare. Check the archive checksums. Extract only <db>.sqlite and its dictionary CSVs. Write one schema.sql per database, from SQLite’s own catalogue and the dictionary. Build one EKOS project per database through the standard pipeline (child processes, with API keys removed, so preparing never calls a model). Record each ledger’s fingerprint, and scan every ledger for leaked benchmark text. Build a column profile and a distinct-value index from the database file; these are kept beside the project, never in a ledger.
  2. Context. For an EKOS cell, the schema text is rendered from the project’s compiled ledger: Table objects with columns, types, keys and descriptions, plus ForeignKey edges as join paths. The column profile is added, and the values the question mentions are looked up.
  3. Generate. One model call with the cell’s prompt. If the SQL does not run, the error goes back once. If it returns no rows or a single NULL (result checks), that fact goes back once. The model is never shown anything about the gold answer.
  4. Score. The predicted and gold SQL run against the same read-only database with a 30-second limit. Result sets are compared with Python’s equality, as the official scorer does (1 == 1.0). Each answer gets an outcome category. Three timed runs feed R-VES.
  5. Report. Each report stores the cell’s configuration and its hash, the prompt hash, ledger fingerprints, the split and a hash of its question ids, and n with a bootstrap interval. It also stores tokens (billed and cached), cost, latency, and every question’s SQL and verdict. compare pairs two runs question by question.

What the results say

  • EKOS’s compiled pack beats raw DDL by 10–14 points with the same model and output limit (EKOS adds five prompt rules and one result check): G 63.9% (a clean hold-out) and G2 66.9%, against 53.3%. Both differences are significant on 302 paired questions.
  • What moved the score (on the tune split): column profiles +11 points; the ekos-v1 prompt with result checks another +12. Raising the output limit from 1,024 to 4,096 tokens removed answers with no SQL at all (9% of the baseline). Voting between three candidates did not pay; value lookup is neutral.
  • formula_1 was worse under the pack (G 18/33 against 26/33) until the profile also counted empty strings. Its lap-time columns record “no time” as both NULL and ''. A profile that reported only the NULLs made the model drop the <> '' filter it writes when it sees raw DDL. G2 fixed it: 26/33.
  • The scorer matches BIRD’s official one. 704 recorded predictions gave identical verdicts from bird-bench/mini_dev’s scorer (Python 3.10, SQLite 3.37.2). One Soft-F1 value differed because SQLite before 3.45 cannot parse 16 nested replace() calls.
  • Not yet measured: the pack with BIRD’s column and value descriptions (fixed in v1.2.0), few-shot examples from BIRD’s train split, a stronger model.
