EKOS — a real question, a real codebase

“When a payment’s status changes,
which code did it?”

The everyday version of this question costs an afternoon: search the Postgres schema, search the backend, search the invoice templates, and still not be sure. We pointed EKOS at LedgerSMB — a real Perl 5 / PostgreSQL double-entry accounting ERP, 1,522 files — and asked it. The answer is one column and one function, and every claim in it resolves to a file and a line.

§ 01 / the problem
Why this takes an afternoon

There is no payment_status column. There are three status fields, and two are decoys.

Each of the three is described — by its own authors or its own schema — as holding payment state. Only one is written by the engine that actually governs it.

workflow.state
Authoritative. varchar(30), written by exactly one function, with every past transition in workflow_history.
payment.closed
Decoy. The schema’s own comment: “This will store the current state of a payment/receipt order”. A boolean that predates the workflow engine.
transactions.approved
Decoy. A bool with approved_by and approved_at. Overlaps the POSTED state without being the same thing.

A search for “payment status” surfaces the two decoys first, because they carry the words payment and state. The authoritative field carries neither.

§ 02 / the answer
One column, one function

Payment status lives in the workflow engine, reached through the general ledger.

payment.gl_id→gl.id→transactions.id⇢workflow.workflow_id→workflow.state

Three of those hops are declared foreign keys. The fourth (⇢) is not a constraint at all — it is the attribute extra_table="transactions" in a persister configuration file. No schema diagram can show it, and no grep for payment or status reaches it, because neither word appears.

lib/LedgerSMB/Workflow/Persister.pm:155
sub update_workflow {
    my ($self, $wf) = @_;
    ...
    # the only write to payment status anywhere in the system
    UPDATE workflow SET state = ?, last_update = ? WHERE workflow_id = ?

lib/LedgerSMB/Scripts/payment.pm — the file whose name promises exactly this — contains no status write at all. Searching for “payment” is what makes the trace hard.

§ 03 / lineage
Requirement 1 — where the data comes from

A payment reaches its status through the ledger, not directly.

§ 04 / the state machine
Why a payment “fails” to approve

Five states, declared in XML — not in any Perl file.

INITIALpost → SAVEDapprove → POSTED batch-delete →DELETED

Whether approve or batch-approve fires is decided by one condition, is-batch-member, defined at workflows/payment.conditions.xml:2 as the test $context->{'batch-id'}, evaluated against the JSON in workflow_context. That is the whole reason a payment “fails” to approve individually: it belongs to a batch.

REVERSED is declared as a state, but no action in payment.workflow.xml transitions into it — a dead state the compiled model makes visible.

§ 06 / the economics
Why a compiler, not a search

A capable model with grep reaches this too. The question is what it costs — and whether it costs that again tomorrow.

StepText searchEKOS
Find the candidates grep -ril payment → 202 files, 3.86 MB ≈ 964,000 tokens to narrow by reading One query → ≈ 938 tokens, ranked, each result carrying its kind and source path
Traverse the join path Not possible. Three foreign keys declared 2,400 lines apart in one 134 KB file — grep matches strings, not edges A graph query over 218 compiled foreign keys
Know what’s real No signal — a comment and a guess look identical sql_comment vs llm_description are separate properties
The second question Full re-exploration, same cost, every time The ledger already exists — another ≈ 1,000 tokens

Amortisation is the real argument. Compiling LedgerSMB read roughly 2.3 M tokens of source once and produced 6,807 objects, 3,114 relationships and 7,677 evidence records. The first question is roughly break-even against a careful manual search. The tenth is not close.

§ 07 / honesty
What EKOS did not do here

Three parts of that report came from reading files by hand.

The convention hop

The transactions → workflow link was read from persisters.xml by hand. EKOS does not model persister configuration, so it appears in the diagram as a convention, never as a compiled fact.

Perl line numbers

There is no Perl analyzer. EKOS observes .pm files and harvests declaration symbols, but builds no call graph — the five functions were confirmed by reading the file.

This schema, yesterday

The same compile returned 8 tables instead of 192 until RFC 0146 landed. One unparseable COMMENT ON was discarding an entire file, behind a single buried warning.

The honest division

The ledger narrows 202 candidate files to six and supplies the graph. Direct reading confirms the lines. Neither half is sufficient alone — and a tool claiming otherwise is the wrong one to trust with an audit trail.

§ 08 / what made it work
RFC 0146 — the dialect only ever understood pg_dump

0 of 158 tables, with the dialect configured correctly.

EKOS’s PostgreSQL dialect had been tuned entirely against pg_dump output, which emits a narrow, mechanical subset of the language. A hand-maintained schema does not. LedgerSMB’s first COMMENT ON TABLE … IS $$…$$ failed the whole-file parse and took every table in the file with it — reported only as one buried SQL001 warning, never an error.

  • Phase 1 — eleven preprocessing transforms for what real schemas write: COMMENT ON, INHERITS, SECURITY DEFINER, RETURNS SETOF, := named arguments, DO blocks, CREATE RULE, psql meta-commands, COPY … FROM stdin payloads.
  • Phase 2 — COMMENT ON text stopped being discarded and became evidence-backed descriptions with real source lines. The schema’s own words now outrank anything a model writes about the same table.
  • Phase 3 — an enrichment token budget computed per file, and a SQL004 diagnostic, because partial coverage used to pass completely silently: 24 of 192 tables named, nothing reported.
