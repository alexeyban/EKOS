Why EKOS uses an LLM at all

EKOS is a compiler for enterprise knowledge. The part that builds the knowledge — observing repositories, databases and documents, recovering tables, symbols, call graphs and lineage, resolving identities, writing an append-only ledger — is deterministic and uses no LLM. Every fact carries the evidence it came from.

People don't ask a ledger questions in EKL, though. They ask “what depends on the redaction module?” or “which RFC introduced the fact-segment engine?”. The LLM sits at the very end: it gets a small, typed evidence set the planner has already assembled, writes the answer in plain language, cites the claims it used, and is expected to say “Insufficient evidence” when the evidence doesn't answer the question. It never touches the source systems.

observe→recover→resolve→compile→ledger→planner + evidence→LLM answer + citations

Where the LLM is used

ekos ask / REASON
Writes the final answer from the evidence set and cites it. This is what the 101-scenario eval grades.
ekos eval run
Runs the suite against a real workspace; grading itself is deterministic keyword and id matching, no LLM judge.
document semantics opt-in
Extracts Concept objects and their relationships from prose documents.
architecture reasoning opt-in
Classifies crate roles; every result is written as reviewable, never as fact.
llm-description opt-in
Adds evidence-grounded ai_overview / ai_usage text to modules and symbols.
docs --prose, rerank, NL-to-SQL opt-in
Prose overviews in generated docs, an LLM rerank of evidence, and the gated ClickHouse query bridge.

Why DeepSeek beats local Ollama here

We changed the model with the knowledge held fixed: same pre-change ledger, same 101 questions, 53 → 70. Four things account for the gap.

  • The context window was silently truncated. EKOS never sent num_ctx, so Ollama used its small default window and dropped the start of any longer prompt — which is where the instructions live. The largest prompt recorded under llama3 was 3,875 tokens — right at that ceiling. DeepSeek's much larger window takes the same prompts whole.
  • Model capacity. An 8B model reads a 60-claim evidence set shallowly: it misses the one claim that answers the question, or answers from an adjacent one.
  • Format and refusal discipline. The answer must end in a machine-readable cited_evidence block and must refuse false premises. llama3 drifted into prose citations and fabricated on adversarial questions; hallucinated answers fell from 7 to 3.
  • It actually finishes. On the 15 GB workstation used here, local answers took up to 79 s at p95 and the eval was killed three times for lack of memory. A fresh DeepSeek call took a median of 5 s; a full 101-question run costs about $0.05–0.08.

What we built between 70 and 87

  • Documents keep their structure. Markdown was cut into blind 2,500-character chunks and only the first 1,200 characters of each were searchable. Each heading is now its own section — named by its heading path, with line ranges, document type and RFC number — and fully indexed.
  • Docs link to code and to each other. A backticked identifier that names exactly one symbol, and an “RFC 0015” mention, become deterministic References edges — 7,377 doc→code and 3,420 RFC→RFC on EKOS's own repository. Ambiguous names never link.
  • The planner asks the right question. A dependency phrase buried in a descriptive clause no longer triggers a graph walk, qualified paths like ekos_common::redaction resolve as one name, and generic words (“crate”, “record”) no longer match unrelated objects.
  • Bugs found by measuring. Every ekos commit since 10 September had left the search index stale for read-only queries; cached answers truncated at a lower token limit kept replaying. Both are fixed with regression tests.

What this means for closed environments

The compile side of EKOS runs anywhere — no GPU, no network, no model. Answer quality is a different matter: it tracks the class of model you can serve. A workstation-sized local model gets you roughly the “before” column. Reaching the “after” column without a cloud API means hosting a much larger open-weights model on dedicated GPU servers, with a context window of at least 32k tokens and enough throughput to answer in seconds rather than minutes.

EKOS supports both shapes today. Point it at any OpenAI-compatible endpoint — a self-hosted vLLM or llama.cpp server inside the network, or a hosted provider — and set the context window explicitly for Ollama:

# hosted (what this post measured)
[llm]
provider    = "openai"
base-url    = "https://opencode.ai/zen/v1"
model       = "deepseek-v4-flash"
api-key-env = "OPENCODE_API_KEY"

[ai]
max-tokens  = 8192   # reasoning model: hidden reasoning counts against this

# local Ollama — never truncate silently again
[llm]
provider       = "ollama"
context-window = 32768

One more reason to self-host in a closed environment: prompts contain real source excerpts. EKOS redacts secrets and PII before anything reaches the ledger, but a hosted model still sees your code. Zen's paid models are zero-retention; its free models may use prompts for training.

What still fails, and why

14 of 101. Grouped by cause:

Premise rejected, but not in refusal wording

adv-004 · adv-011 · adv-015

Questions built on a false premise (“which vendor licenses the vector index to EKOS?”). The model correctly rejects the premise — “the evidence does not confirm…”, “EKOS is MIT-licensed, free of charge” — but the grader only accepts an explicit refusal. Whether to widen the grader or tighten the prompt is still an open decision.

The answer never reaches the top of the evidence

code-002 · lin-008 · dep-004

The function that builds the LLM provider ranks below the provider trait itself; the cited_evidence convention isn't in the evidence the planner retrieves for that question; Rust import-path objects don't link back to the crate that consumes the redaction module.

Facts the compiler doesn't record yet

code-004 · lin-007 · dep-005

The Rust edition is set once in the workspace Cargo.toml and inherited, so no per-crate fact carries “2024”. Struct fields such as KirEvidence.confidence aren't emitted as claims. No caller of plan_question reached the evidence set, so the model correctly says it can't answer — which the grader scores as ungrounded.

Ranking, not answering

arch-009 · hist-007

Retrieval-only scenarios graded on recall@10. With documents now split into many sections, those sections outrank the crate or file the scenario expects. This is also why recall@10 fell while answers improved.

Right in substance, wrong keyword

arch-020 · sec-002 · sec-010

“Objects can't be deleted from the append-only ledger” without the word “tombstone”; “the security section is additive only” where the grader expects “extend”.

Measurement notes. The before run was measured on a different rebuild of the ledger, likely partly affected by the stale-index bug. The model-swap-only run (70) used a 2,048-token output limit that cut off 17 answers, so the model's own contribution is if anything understated.
