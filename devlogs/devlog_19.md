# Devlog 19 — RFC 0017 Crypto Connector: DeFi Sentinel ingestion, plus a latent EKL bug

**Date:** 2026-07-20
**PRs:** worked on `main` (single session)
**Branch:** main

---

## Summary

Implemented the first external, cross-language consumer of EKOS: the DeFi Sentinel Platform
(a separate Python repo) needed to reuse EKOS's ledger/evidence store rather than build its own
graph. Wrote RFC 0017, then built `ekos-plugin-crypto` (an `Observer` reading Parquet exports)
and `CryptoAnalyzerPass` (a recovery pass mapping them to KIR), following the existing
Observer→recovery-pass pipeline exactly — `compile`/`commit` needed zero changes. Verified against
two real fixtures generated by DeFi Sentinel's actual Python exporter (not hand-written JSON): a
small one covering all three relationship kinds, and a 93-entity batch from one real pump.fun
discovery cycle. Along the way, found and fixed a real, previously-latent bug in EKL's relationship
`kind` formatting that this connector's first-ever use of `RelationshipKind::Custom` exposed.

## What was built

### RFC 0017 — Crypto Connector

Docs: `docs/rfcs/0017-crypto-connector.md`. Key decision: Observer + recovery-pass pattern
(matches `SqlAnalyzerPass`/`GitAnalyzerPass`), not the `build.rs` inline shortcut `FileObserver`
uses — the crypto export carries objects/relationships/evidence together, the shortcut only ever
constructs bare objects. This means `compile`/`commit` required **zero code changes**: their
`ckm_object_to_kir`/`ckm_rel_to_kir` already handle arbitrary `Custom` kinds generically.

### `ekos-plugin-crypto` (new crate)

`CryptoObserver` implements `Observer`; reads the latest `batch_id=<ts>/` directory under an
export root via an injected `CryptoExportReader` trait (constructor-injection pattern from RFC
0012's `SalesforceClient`). `ParquetExportReader` is the real implementation — uses the `parquet`
crate's row-level `record`/`RowAccessor` API only, no `arrow` dependency, no native/system
libraries (unlike the SAP/Oracle native-dependency problem RFC 0012 hit). `MockCryptoExportReader`
returns a fixed batch for unit tests.

Registered in `build.rs` **conditionally**: only added to the observer list when
`EKOS_CRYPTO_EXPORT_DIR` is set (soft-skip, mirrors how `recover.rs` already selects an LLM
provider off `ANTHROPIC_API_KEY`). Most `ekos build` runs in this repo self-observe and have no
crypto export — that's a normal state, not a misconfiguration.

### `CryptoAnalyzerPass` (in `ekos-recovery`)

Modeled on `GitAnalyzerPass`: reads artifact IDs from `ctx.artifact_store` during `run()`, not at
construction. Maps entities → `ObjectKind::Custom(kind)`, relationships → `RelationshipKind::Custom(kind)`,
evidence → `KirEvidence`. KirIds are derived deterministically via `Uuid::new_v5` over the export's
own stable `entity_id`/`evidence_id` strings — the same wallet appearing across many 15-minute
batches resolves to the *same* `KirObject`, verified by a test asserting two batches with an
identical entity produce exactly one deduplicated object with the expected id. A relationship
referencing an entity outside its batch is skipped with a diagnostic, not a hard failure — exports
are batch-scoped and this can happen legitimately.

No LLM step, unlike `SqlAnalyzerPass` — the crypto data is already typed and named by its
producer; there's nothing for an LLM to enrich.

### Fixtures: real producer output, not invented JSON

`plugins/crypto/tests/fixtures/`:
- `sample_batch/` — small, but generated by actually calling DeFi Sentinel's Python
  `export_batch()` function against hand-seeded (but realistic) rows, so the Parquet encoding
  itself is genuine. Covers DEPLOYED, ASSOCIATED_WITH, and LINKED_TO in one batch.
- `live_batch/` — output of one real `sentinel run pipeline-cycle` in the DeFi Sentinel repo
  against live DexScreener/GeckoTerminal APIs: 93 real pump.fun-launched token/social entities.

Same "near-real data" convention RFC 0012 established for the Salesforce/SAP/etc. fixtures.

## Bug found: EKL relationship `kind` used Debug, not Display

`crates/ekl/src/interpreter.rs`'s `relationship_row` formatted `kind` with `format!("{:?}", rel.kind)`
— Debug — while `object_row` correctly used `obj.kind.to_string()` — Display. For every built-in
`RelationshipKind` variant (`ForeignKey`, `CoupledWith`, ...), Debug of a bare unit variant happens
to produce the same string as Display, so `WHERE kind = 'ForeignKey'` worked by coincidence. The
first relationship anywhere in this codebase to use `RelationshipKind::Custom(String)` — my
crypto connector's `DEPLOYED` edge — exposed it immediately: Debug renders `Custom("DEPLOYED")` as
the literal string `Custom("DEPLOYED")`, not `DEPLOYED`, so `FIND Relationship WHERE kind =
'DEPLOYED'` silently returned zero rows against a ledger that actually had one.

Fix: one line, `rel.kind.to_string()` instead of `format!("{:?}", rel.kind)`, matching
`object_row`. Added a regression test (`finds_relationships_of_a_custom_kind`) asserting a
`Custom("DEPLOYED")` relationship is found by `WHERE kind = 'DEPLOYED'`. All 25 pre-existing EKL
tests still passed both before and after — nothing depended on the buggy behavior.

## Knowledge Captured

- **Debug vs Display on enums with a `Custom(String)` fallback is a trap.** `#[derive(Debug)]`
  renders `Custom("x")` literally; only `Display` (when hand-implemented to special-case the
  variant) collapses it to `x`. Any code formatting a KIR `kind` field for display or comparison
  must use `.to_string()` (Display), never `{:?}`. `object_row` had it right; `relationship_row`
  didn't — worth a targeted grep (`{:?}.*kind` or similar) if another Custom-bearing field shows up
  formatted somewhere new.
- **A bug in a taxonomy's "safe to add Custom values" claim only surfaces when something actually
  uses a non-built-in value.** RFC 0012's Salesforce/SAP/etc. connectors never used
  `RelationshipKind::Custom` (they only emit `ObjectKind`s from `describe()` calls, no
  relationships beyond raw reference-field data). This connector was the first to close that loop
  end-to-end for relationships specifically, which is exactly why the bug had never been caught.
- **The Observer → recovery-pass pipeline genuinely doesn't need touching `compile`/`commit`** for
  a new connector, confirmed by reading `commit.rs`'s conversion functions before writing any code
  — they already handle arbitrary `ObjectKind`/`RelationshipKind` values generically. Worth
  remembering as the default assumption for the *next* connector too, rather than re-verifying from
  scratch.
- **`ConnectorConfig`/`ekos.toml` `[connectors.<name>]` parsing is documented in
  `observation-sdk`'s doc comments but not implemented anywhere** — no crate reads it from
  `ekos.toml`, no observer calls `ScanContext.with_config`. Every connector to date (including this
  one) uses constructor injection or an env var instead. Don't assume that config surface exists
  without checking; it's aspirational until someone actually wires it.
